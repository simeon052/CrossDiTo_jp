# ESP32-S3 でファームが起動しなくなる罠と、原因の追い方

CrossDiTo_jp（Xteink X4 Pro / ESP32-S3 / PSRAM 8MB / Arduino-ESP32）を触っていて踏んだ事柄のうち、**この製品に限らず ESP32-S3 のファームウェア一般に当てはまるもの**をまとめた。実機を1台しか持たずに開発していて、焼いたら起動しなくなった、という状況を想定している。

機種固有の手順（パーティションの配置、復旧コマンド）は [Installation](./installation.md) に、縦書き組版の話は [日本語対応](./japanese.md) に分けてある。

---

## 1. `.flash.text` が 64KB 境界の直前に着地すると起動しない

**いちばん質が悪い。ビルドもリンクも成功し、焼くまで分からない。**

### 症状

```
ESP-ROM:esp32s3-20210327
...
entry 0x403c8870
E (941) cpu_start: Invalid app image header
abort() was called at PC 0x...        （= system_early_init）
Rebooting...
```

これが延々と繰り返る。e-ink なら画面は前の絵のまま変わらず、電源ボタンも効かない（アプリが初期化を抜けられないので、ボタン処理に到達しない）。一見すると文鎮化したように見えるが、**ROM ブートローダは生きているので USB から書き直せば戻る。**

### 原因

ESP32-S3 では flash の rodata（DROM）と PSRAM が**同じアドレス領域**を使う。そのため ESP-IDF の `sections.ld` は、rodata の開始位置を「`.flash.text` のぶんだけ空ける」形で決めている。

```ld
.flash_rodata_dummy (NOLOAD):
{
  _flash_rodata_dummy_start = .;
  . = ALIGN(ALIGNOF(.flash.text));
  . = SIZEOF(.flash.text);              /* .flash.text と同じ大きさの空隙 */
  . = ALIGN(_esp_mmu_block_size) + 0x20;
  _rodata_reserved_start = .;
} > default_rodata_seg
```

ところが `drom0_0_seg` の原点は `0x3C000020` で、**64KB 境界から 0x20 ずれている**。この 0x20 はイメージヘッダのぶんである。

結果として、`.flash.text` が 64KB 境界の**直前 0x20 バイト**に着地すると、

- 空隙は 64KB 単位に丸められて **N ページ**
- 実際の命令セグメントはヘッダ 0x20 を含むため **N+1 ページ**にまたがる

となり、1ページ足りない。命令側とデータ側は MMU のページテーブルを分け合うので、データ側の割り当てが1ページずれる。起動直後にイメージヘッダを読む処理（`system_early_init`）が別の内容を読んで「ヘッダが不正」と判断し、`abort()` する。

実際に配布してしまった3版の実測値：

| 版 | 命令領域の大きさ | 必要 / 確保 | 余裕 | 結果 |
|---|---|---|---|---|
| A | `0x24FBB4` | 37 / 37 ページ | **+1,068 B** | 起動する |
| B | `0x250060` | 38 / 37 ページ | **-128 B** | 起動しない |
| C | `0x250008` | 38 / 37 ページ | **-40 B** | 起動しない |
| D（修正後） | `0x250128` | 38 / 38 ページ | **+65,208 B** | 起動する |

A はたまたま 1KB の余裕で通っていただけで、約 1.1KB の機能追加で踏み抜いた。**機能の内容とは何の関係も無い。**

### 検出する

イメージのセグメント表から機械的に判定できる。ELF でなく、焼く対象の `.bin` そのものを見るのが確実。

```python
# 共通ヘッダ8 + 拡張ヘッダ16 のあと、各セグメントは (load_addr, length) が先頭に付く
def segments(image: bytes):
    count = image[1]
    offset = 24
    out = []
    for _ in range(count):
        load, length = struct.unpack("<II", image[offset:offset + 8])
        offset += 8 + length
        out.append((load, length))
    return out
```

命令セグメント（`0x42000000` 台）とデータセグメント（`0x3C000000` 台）を拾って、

```
必要ページ数 = ceil((命令のロードアドレス % 64KB + 命令の長さ) / 64KB)
確保ページ数 = (データのロードアドレス - 0x3C000020) / 64KB
```

を比べる。`確保 < 必要` なら起動しない。この判定は本リポジトリの `scripts/check_image_mmu_split.py` にある。CI とリリースの両方に組み込み、**起動しないイメージが配布経路に乗らないようにしてある。**

### 直す

`.flash.text` を**境界の手前で止めずに、越えさせる**。越えれば空隙は次のページまで取られるので、余裕が一気に 64KB 近くまで広がる。削って手前に収めるのは、余裕が数十バイトしか無いので次の変更でまた踏む。

詰め物を入れるときに2回失敗したので、そこも書いておく。

**効かない書き方1 — `const` 配列に `section(".text")`**

```cpp
// データとして扱われ rodata 側に載る。.flash.text は動かない
extern "C" __attribute__((used, section(".text"))) const unsigned char pad[256] = {};
```

**効かない書き方2 — 参照の無い関数**

```cpp
// used はコンパイラ側の削除を止めるだけ。-Wl,--gc-sections が落とす
extern "C" __attribute__((used, noinline)) void pad() { asm volatile(".space 256"); }
```

Arduino-ESP32 のリンクフラグには `-Wl,--gc-sections` が入っている。参照されていないセクションはリンカが捨てる。

**効く書き方 — 関数にして、実行されない形で参照を作る**

```cpp
extern "C" __attribute__((used, noinline)) void mmuSplitPad() { asm volatile(".space 256"); }

void setup() {
  // --gc-sections から守る。アドレスを触るだけで、呼びはしない
  volatile uintptr_t keep = reinterpret_cast<uintptr_t>(&mmuSplitPad);
  (void)keep;
  ...
}
```

`volatile void (*p)()` は「volatile 修飾された**関数**へのポインタ」であって「volatile な**ポインタ**」ではない。コンパイルエラーになるので `uintptr_t` で持つのが素直。

ESP-IDF 側のリンクフラグに合わせるなら `-Wl,-u,mmuSplitPad` でも同じことができる。

## 2. コアダンプの読み方と、いちばん踏みやすい罠

### 取り出す

コアダンプ領域の位置はパーティション表から読む。決め打ちしない。

```sh
esptool --chip esp32s3 --port /dev/ttyACM0 read-flash 0x8000 0xC00 parttable.bin
```

エントリは32バイト固定で、先頭2バイトが `0xAA 0x50`。

```python
magic = e[:2]                                   # b"\xaaP"
type_, subtype = e[2], e[3]                     # subtype 0x03 = coredump
addr, size = struct.unpack("<II", e[4:12])
label = e[12:28].split(b"\x00")[0].decode()
```

その位置と大きさで読み出す。

```sh
esptool --chip esp32s3 --port /dev/ttyACM0 read-flash <addr> <size> coredump.bin
```

### 中身

**24バイトのヘッダのあとに ELF が始まる。** `coredump.bin[24:]` が ELF で、そこからは普通のコアダンプとして読める。

- `PT_NOTE` セグメントにノートが並ぶ
- `NT_PRSTATUS`（type=1）がタスクごとに1つ。`desc[24:28]` が TCB アドレス、`desc[72:76]` が PC
- `ESP_EXTRA_INFO` ノートの先頭ワードが**落ちたタスクの TCB**、以降は key/value の並び
  - `0xE8` = EXCCAUSE、`0xEE` = EXCVADDR、`0xB1` = EPC1
- `PT_LOAD` セグメントに各タスクのスタックと TCB の中身が入る

**EXCCAUSE 65** は `XCHAL_EXCCAUSE_NUM + 1`、つまり「未処理のデバッグ例外」で、実際には **FreeRTOS がスタック末端に置いたウォッチポイントの発火＝スタック溢れ**を意味する。

タスク名は TCB の中にあるが、`configMAX_TASK_NAME_LEN` は 16 なので**長い名前は切れる**。`ActivityManagerRender` が `ActivityManager` に見えて、別のタスクと取り違えかけた。

スタックの範囲も TCB から取れる。ワード12が `pxStack`、ワード18がスタック終端のことが多い（FreeRTOS のビルド設定による）。差を取れば**そのタスクに与えられたスタックの大きさ**が分かる。

### いちばん踏みやすい罠：コアダンプは読み出しても消えない

**ダンプ領域は、新しいクラッシュが書かれるまで古い記録を保持し続ける。**

このとき何が起きるか。

1. 事象Xでクラッシュ → ダンプが書かれる
2. 事象Yで**ハング**（パニックではない）→ ダンプは**書かれない**
3. ダンプを読み出すと**事象Xの内容が出てくる**
4. それを事象Yの原因だと思って、見当違いの修正をする

実際にこれをやった。「OTA 中に描画タスクのスタックが溢れた」という診断でリリースまで出したが、そのダンプは前の事象のもので、スタック溢れは起きていなかった。

**見破り方**：ダンプの中の値が、**いま動かしているビルドの設定と整合するか**を先に確かめる。今回はダンプ内のスタックが 8,180 バイトで、これは変更前のビルドの値だった。現行ビルドなら 16,380 のはずで、その時点で「古い」と分かった。ほかにも、動いていないはずのタスク（`wifi` など）が居ないか、タイムスタンプが辻褄に合うか、といった見方がある。

なお、パニックハンドラがダンプを書けないこともある。

```
E esp_core_dump_flash: Core dump flash config is corrupted! CRC=0x... instead of 0x0
E esp_core_dump_common: Core dump write failed with error=-1
```

こうなっていたら、そのクラッシュのダンプは**存在しない**。

### アドレスを関数名にする

ELF があればシンボルテーブルを引くだけで、専用ツールは要らない。

```python
# .symtab から STT_FUNC のシンボルを集め、アドレスで二分探索する
n, val, size, info, other, shndx = struct.unpack("<IIIBBH", sym_entry)
if size and (info & 0xF) == 2:          # STT_FUNC
    ...
```

リリースビルドの ELF が手元に無くても、**同じコミットの CI ビルドの ELF**でだいたい足りる。バージョン文字列の長さの差でアドレスは多少ずれるが、関数の特定には困らない。

## 3. 二面構成（OTA スロット）の扱い

アプリ領域が2面あり、どちらを起動するかは `otadata` が決める。

- OTA や SD カードで更新した端末は `app1` から起動していることがある
- その状態で `app0` にだけ書いても、**書き込みは成功するのに画面が何も変わらない**

**両面に書けば、どちらが選ばれても新しいファームが起動する。**

```sh
esptool --chip esp32s3 --port /dev/ttyACM0 --baud 460800 write-flash 0x10000 fw.bin 0x7f0000 fw.bin
```

`Hash of data verified.` が**書いた領域の数だけ**出ることを確認する。

注意点がいくつかある。

- **リポジトリの `partitions.csv` と、端末が実際に使っている表は別物でありうる。** パーティション表を焼いていないなら、端末が使うのは工場出荷時のもの。実機から読んで確かめる
- **`erase-flash`（全消去）は使わない。** `0x0` の2段目ブートローダと `0x8000` のパーティション表まで消える。プロジェクトがそれらを配布していないなら、復旧できなくなる
- ブートループに入った端末では、**ボタン操作による SD カード復旧も使えない**。その判定はアプリの中にあり、そこへ到達する前に落ちているため。USB から書くしかない

## 4. リリースビルドでシリアルログが無くても、ブートローダは喋る

アプリ側のシリアルログを無効にしたリリースビルドでも、**ESP-IDF のブートローダと ROM は UART に出力する**。起動しない端末の切り分けでは、これだけで足りることが多い。

```sh
python -m serial.tools.miniterm /dev/ttyACM0 115200
```

つないだまま電源を入れ直して、出方で分ける。

| 見え方 | 意味 |
|---|---|
| ROM の行が出て、アプリのログの直前で静かになる | ブートローダは動いている。**アプリが固まっている** |
| `ota_1 is not bootable` / 同じ出力の繰り返し | **`otadata` とスロットの状態**の問題 |
| `E (...) cpu_start: Invalid app image header` が繰り返る | 上記 1 の境界の罠 |
| 何も出ない | フラッシュかハードウェア側 |

esptool が入っていれば pyserial も入っているので、追加インストールは要らない。

## 5. 切り分けの順番（これを守らず遠回りした）

### 起動しなくなったら、まず最後に動いていた版を焼く

今回、原因究明にいちばん効いたのはこれだった。にもかかわらず後回しにして、イメージのハッシュ照合、ビルド環境の比較、セグメント構成の解析を先にやった。

- **古い版が起動する** → 原因はファームの中身。そこから二分すればよい
- **古い版も起動しない** → 原因はフラッシュの状態か端末側。見る場所がまったく変わる

この1回の書き込みで、調べる範囲が半分になる。先にやるべきだった。

### 「直した」と言う前に、出力が変わったことを確かめる

修正を入れたのに**出力が1ビットも変わっていない**ことが2回あった。

- 縦組みのずれを直したつもりが、スクリーンショットの PNG が修正前とバイト単位で同一だった（条件が空振りしていた）
- 詰め物を入れたつもりが、命令領域が 4 バイトしか増えていなかった（リンカが落としていた）

どちらも「変わったはず」で報告していたら、間違った説明のまま次に進んでいた。**成果物が実際に変わったかを、報告の前に見る。**

### 数ピクセルのずれは、写真ではなく画素で詰める

実機の写真を見て「まだずれて見える」「直った気がする」を往復するのは、時間がかかるわりに何も確定しない。シミュレータに同じ本と同じ設定を読ませて PNG を持ち帰り、**墨の位置を数値で比べる**ほうが速く、しかも修正前後の差を証拠として残せる。

縦組みの文字の中心ずれは、この方法で「0.5px なので無関係」「4.5px あるので本物」と切り分けられた。目では区別できない差だった。

### 一瞬しか出ない画面は、撮影の間隔と開始時刻を変える

スリープ画面のように数フレームで次へ進む画面は、既定の撮影間隔では1コマも入らない。撮影の**開始時刻・間隔・終了時刻**を指定できるようにしておくと、こういう画面も押さえられる。

## 6. その他、ESP32 一般で効いた小ネタ

### フォントなど「ページ単位で遅延ロードする資源」を測るとき

SD カードのフォントのように、**そのページに出てくる字ぶんしか読み込まない**仕組みでは、載っていない字の寸法を測ると置換字形の値が返る。黙って間違った値が返るのがたちが悪い。

レイアウトの基準値を「特定の1文字を測って決める」と、その字がページに無いときだけ崩れる。**ページの内容に依存しない値**（フォントの行送りなど）から取るか、その行に実在する文字から取る。

実際、全角セルの幅を「あ」で測っていたため、本文に「あ」が無いページだけ欧文が 5px ずれていた。ページによって出たり消えたりするので、写真では条件が掴めなかった。

### `used` と `--gc-sections` は別の話

`__attribute__((used))` はコンパイラに「この定義を出力しろ」と言うだけで、**リンカの `--gc-sections` には効かない**。参照の無いセクションは落ちる。リンカにも残させるには、実際に参照を作るか `-Wl,-u,<symbol>` を使う。

### ヒアドキュメント越しにソースを書くときのバックスラッシュ

シェルのヒアドキュメント経由でスクリプトを流し込むと、環境によってはバックスラッシュが一段潰れる。`'\\0'` のつもりが `'\0'`（NUL 1バイト）としてソースに書き込まれる、といった事故が起きる。エスケープを含む文字列を生成するコードは、バイト列で組み立てて、書いたあとに `open(f,"rb").read().count(b"\x00")` で検査するのが安全。

## まとめ

- **ビルドが通ることと、起動することは別**。ESP32-S3 では `.flash.text` の大きさだけで起動しなくなる。焼く前に機械的に検査できるので、CI に入れておく
- **コアダンプは消えない**。読む前に、その内容がいま動かしているビルドと整合するか確かめる
- **起動しなくなったら、まず最後に動いていた版を焼く**。調べる範囲が半分になる
- **「直した」の前に、出力が変わったことを見る**
